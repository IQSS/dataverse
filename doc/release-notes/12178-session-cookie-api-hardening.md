A new feature flag, `dataverse.feature.api-session-auth-hardening`, adds a same-site check to API requests authenticated with a logged-in session (the JSESSIONID cookie). When enabled, the browser must prove the request originated from the same site configured in `dataverse.siteUrl` -- using the `Origin` and `Referer` headers that browsers set automatically and that page scripts cannot forge.

**For administrators:** This flag can be used in two ways. First, enable it on its own to harden the Access API (used for file downloads), which has always accepted session cookies without any same-site check. Second, enable it together with `dataverse.feature.api-session-auth` to safely allow session-based API authentication in production. Previously, `api-session-auth` was recommended only for local testing because it exposed the installation to cross-site request forgery (CSRF) attacks. With this hardening flag, cross-site requests are blocked, making it practical to use session authentication for front-end code -- such as React components embedded in the JSF pages -- that needs to call the full API on behalf of the logged-in user.

**For end users:** Normal browsing and file downloads from the Dataverse interface work exactly as before. The main change is that a restricted file opened via a bookmarked or shared link will no longer automatically use your logged-in session, because the browser does not send the required headers for a standalone URL. The same file will still download when you click a link from within the Dataverse site itself. Public files are unaffected.

See [the guides](https://guides.dataverse.org/en/latest/installation/config.html#dataverse-feature-api-session-auth-hardening) for configuration details.
